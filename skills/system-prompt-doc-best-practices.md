# 系统提示词文档创建最佳实践

> 本 skill 由 `@local/dsh-prompt-mode` 插件提供。基线正文是固定的；末尾「已积累的经验教训」段落由 `prompt_doc_learn` 工具不断追加，加载时请一并读完。

## 这份 skill 解决什么问题

同一件事，「裸说」给 Agent 的效果一般；先把任务写成一份**系统提示词文档**，再让 Agent「先读这份文档，然后开始」——效果明显更好。这不是玄学，原因有四条：

1. **意图被冻结**：裸说的需求散在对话里，Agent 每一轮都要重新猜；文档把意图固定成文件，第一步读它，后面每一步都能回查。
2. **事实源被点名**：规格、计划、参考图、被改的代码文件，全部写成绝对路径。Agent 不再"大概在 docs 里"，而是直接读对的那个文件。
3. **技能被预先路由**：「这个阶段该加载哪个 skill」不再靠模型临场想起来，而是文档里一张按任务场景索引的表。
4. **验收被前置**：验收标准写进开场指令，Agent 从第一步就知道什么算做完，不会做完才发现方向错了。

所以本 skill 的产出物是一份**下一个会话照着就能干**的系统提示词文档，外加一行可以直接粘贴的交接提示词。

## 一、文档标准

文档必须完全符合下面的结构。`prompt_doc_write` 会按这个结构渲染，`prompt_doc_audit` 会按这个结构打分。

### 1.1 元信息块（文档头部，`>` 引用块 + 加粗键）

| 键 | 必填 | 写什么 |
|---|---|---|
| 版本 | 是 | 日期（`2026-09-25`）或 `vN`。**每次实质修改都要变**，否则读的人不知道手里是不是最新版 |
| 适用任务 | 是 | 这份文档驱动什么任务、边界到哪，一句话说清 |
| 使用方法 | 是 | 交给用户的动作，标准写法：「每次开新会话让 Agent 先读这个文件作为系统 prompt」 |
| 前置条件 | 否 | 需要先存在的产物或环境（某个 `.blend`、某个已装好的依赖、某个已通过的阶段） |
| 目标 | 否 | 要抵达的终态，与「适用任务」互补（一个说做什么，一个说做到什么样） |

### 1.2 七个正文章节（顺序固定）

| # | 章节 | 写什么 | 判定标准 |
|---|------|--------|---------|
| 1 | 角色与目标 | Agent 是谁 + 最终交付什么 | 2–5 条，能让人一眼看出"这是个什么工种、交什么货" |
| 2 | 必须加载的技能（按任务自动触发） | `\| 任务场景 \| \`skill-name\` \|` 表格 | 每个名字都能在技能 catalog 里查到，**不许编** |
| 3 | 数据源（全部在本地工作目录） | 规格 / 计划 / 参考图 / 代码文件的绝对路径表 | 每条路径都真实存在；写清"这份文件是什么的唯一事实源" |
| 4 | 执行顺序（严格按依赖） | `### Step 0/1/2…` 或 `### Round 0/1/2…` | Step 0 永远是环境/前置探测；每步写明依据哪个数据源、加载哪个 skill |
| 5 | 硬性约束（踩坑前知道） | 已踩过的坑、协议限制、命名规范、明确禁止的手法 | 是"踩过才知道"的东西，不是常识；能有 ❌/✅ 对照最好 |
| 6 | 验收标准 | 可判定的条目 | 能写成命令、阈值、或可勾选清单；不要"效果良好"这种词 |
| 7 | 立即开始 | 前 2–4 个动作 + 一句加粗祈使句 | 读完就能动手，不需要再问 |

### 1.3 交接提示词

固定格式，一字不改：

```
请先读 <文档绝对路径>，然后开始 <入口>。
```

例：`请先读 d:\XiaoProject\HanMaXiaoArtExhibition\docs\blender-agent-prompt.md，然后开始 Phase 1 搭建。`

入口写的是**文档里第一个可执行步骤的名字**（`Phase 1 搭建`、`Round 0 基线`、`Step 1 体块`），不是"开始执行"这种空话。

## 二、工作流

```
prompt_doc_plan   → 扫真实仓库，拿真实路径 + 技能候选 + 已有文档
（读关键数据源）   → 抄数字、抄约束、抄路径，不自己估
prompt_doc_write  → 按标准渲染并落盘，逐条校验数据源与 skill 名
prompt_doc_audit  → 审到 PASS
（交付 handoff）   → 一行交接提示词
prompt_doc_learn  → 复盘一条教训，喂回本 skill
```

### 2.1 `prompt_doc_plan` 要用够

- `task` 写用户的原话意图，不是你的转述。
- 返回的 `files` 是**唯一合法的路径来源**。文档里出现的每个路径都必须来自这里，或来自你实际读过并确认存在的文件。
- 返回的 `skillCandidates` 是按任务描述打分排序的。通常每 1–2 个执行阶段配 1 个 skill；超过 5 个就说明你该拆阶段了。
- `prompts` 分组里是**以前生成过的系统提示词文档**。写新文档前先读一份，学它的颗粒度和口吻，也避免重复造轮子。

### 2.2 读数据源要抄不要编

规格文档里的数字（尺寸、阈值、版本、端口、路径）一律照抄。规格之间冲突时，在文档里写明冲突以及以谁为准（例：「Spec 里的数字可能是估算值，当数字和图片矛盾时，以图片视觉为准」）。

### 2.3 每个阶段都要有"依据 + 技能 + 产出"

一个合格的 Step 长这样：

```markdown
### Step 3 · 环形柱廊 + 柱廊标准开间（最关键复用单元）

依据 `柱廊标准开间Spec.md` + `中庭主场景Spec.md`：
- 开间 3-3.5m 宽 × 1.5-2m 深；柱高 6-7m
- **加载 `blender-procedural-systems`** 用 Array Modifier 环形复制
- 先做一个完整开间模板，再阵列
```

有依据、有数字、点名 skill、说清产出顺序。缺任何一样，下一个 Agent 就会自由发挥。

## 三、硬性规则

1. **路径必须真**。写进文档前逐条确认存在。不确定的写「待确认」，绝不编。
2. **skill 名必须真**。去技能 catalog 里核对；名字写错等于没写。
3. **Step 0 永远是探测**。连不上、环境不对、前置产物不在，后面全是白干。
4. **约束必须来自真实失败**。「不要用 `nodes["Background"]`，用 `next(n for n in nodes if n.type == "BACKGROUND")`」这种条目才有价值；「注意代码质量」是噪音。
5. **验收必须可判定**。「偏差 ≤ 5cm」「无孤立面、无重叠相交」「ΔE < 10」是验收；「效果好」不是。
6. **文档用用户的语言**；路径、skill 名、命令保持原样不翻译。
7. **交付只给交接提示词**。不要把文档全文贴回对话——用户要的是一行能粘贴的东西。

## 四、常见翻车

| 翻车 | 症状 | 正确做法 |
|------|------|---------|
| 编路径 | 文档里写 `docs/spec.md`，实际叫 `docs/规格说明.md` | 只从 `prompt_doc_plan` 的结果里取路径 |
| 技能表凑数 | 写了 9 个 skill，实际只有 2 个相关 | 按 `skillCandidates` 的分数取，宁少勿滥 |
| 章节变计划书 | 「执行顺序」写成三段背景介绍 | 每一步都是可执行动作，不是叙述 |
| 验收不可判定 | 「视觉上接近参考图」 | 拆成可对照的视觉签名清单（V1–V6 那种） |
| 约束写常识 | 「要写注释」 | 写"踩过才知道"的坑 |
| 忘了版本 | 改了文档但版本还是旧的 | 每次实质修改都更新版本 |
| 交接提示词太长 | 把整份文档贴进新会话 | 只给「请先读 X，然后开始 Y。」 |

## 五、为什么交接给"新会话"效果更好

生成文档的会话已经装了满脑子的探索过程、试错和中间结论；新会话的上下文是干净的，读文档时没有任何先入为主的假设，只会照着文档做事。这正是效果提升的来源。所以：

- 文档要**自洽**：不依赖生成它的那次对话。
- 文档要**够具体**：新会话不知道你们聊过什么。
- 一份文档对应**一类任务**，不是一次性任务清单。任务推进到新阶段时，写下一份（`-iteration-`、`-phase2-`）而不是把旧文档撑大。

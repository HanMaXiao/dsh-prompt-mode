# Agent Note: 原子落盘与串行追加

Status: implemented

## Problem

本包有两条写路径，都能毁掉已经完成的工作，而且毁法都是静默的。

`prompt_doc_write` 把渲染好的 markdown 直接写到目标路径上。`writeFileSync` 是先截断再写，所以一次中断的写入留下的是一份半渲染的文档，而原来那份完整的已经不见了。工具返回的交接行指向的正是这个路径——用户拿到的是一份看起来像样、其实缺了后半截的文档。

`LessonsStore.add` 更糟。它把「读 `lessons.json`、按当前条数推 id、整体写回」当成三个独立的步骤，于是两次重叠的 `prompt_doc_learn` 会读到同一个条数、推出同一个 id，而第二次写入把第一次那条悄悄覆盖掉。而这还只是并发那一种坏法：`readSync()` 用一个 `catch` 把 JSON 解析失败回答成「空历史」，所以**一份写裂了的 `lessons.json` 读回来是零条教训**——不是报错，是零条。裂掉的存储让整个教训库无声归零，而那些教训是拿真实返工换来的。

两条路径的共同点是：失败都发生在该看见的地方之外。工具调用看起来成功了，skill 下一次加载时只是变短了一点。

## Decision

一个 `writeFileAtomic(target, content)`，放在 [`lib/lessons.js`](../../../../lib/lessons.js)，两条写路径共用：

- 先写一个**和目标同目录**的兄弟临时文件，再 `renameSync` 盖到目标上。同目录是硬要求——跨设备的 `rename` 会以 `EXDEV` 失败，放 `os.tmpdir()` 是把一种失败换成另一种。
- 临时文件名带 `pid` + 时间戳 + 进程内自增计数，所以同一进程里的并发调用不会互踩。
- 写或重命名失败时，临时文件一律 `rmSync(..., { force: true })` 清掉，错误信息带上目标路径和原因。一次失败的写入不留残渣给下一个读者绊倒。
- 替换因此是**一步完成**的：读者看到的要么是旧内容，要么是新内容。

`LessonsStore.add` 把读、推 id、写回包成一个 unit，通过一个进程内的 `MutationQueue` 串行执行。关键性质是这个 unit **同步且从不在读和写之间挂起**，所以调用方到达时队列总是空闲的、当场跑完自己的 unit 并拿回结果。发现队列忙的那个调用方，看到的是一个中途让出了的 unit；它没法同步等一个结果，所以这次调用被**拒绝**——错误信息是 `another write to <file> is still in flight; retry this call so no lesson is lost`。被拒绝的调用可以重试，被允许竞争的调用会永久丢掉一条教训。

`prompt_doc_write` 在 [`host.js`](../../../../host.js) 里改调这一个函数，`lessons.json` 的格式和 `add()` 对外的返回形状都没变（`{ version: 1, lessons: [...] }`、`{ record, total, file }`），所以没有迁移、没有读者被打断。

一处刻意的例外，记在此以免后来者以为漏了：`writeMirror`（那份给人看的 skill 镜像）仍然用普通 `writeFileSync`。它是每次加载都会被重写的派生产物，写裂了代价是重渲染一次，不是丢教训；把它也包进原子写入会给一条不需要一步到位的路径加上临时文件和重命名的成本。

## Alternatives considered

**保持直接写目标，只把错误抛出来。** 这是改动前的形状，也是读起来最省事的。它输在时序上：`writeFileSync` 在失败落地之前就已经把目标截断了，所以「抛出错误」救不回已经没了的那份内容——错误只告诉你毁了，不保留原文。原子性不能靠错误处理补，只能靠替换步骤本身不可分。

**先备份旧内容，失败时恢复。** 直觉上很稳：旧文件还在，坏了就拷回去。它把一次一步到位的替换换成了一套有自己失败模式的恢复协议——恢复那次写入自己也可能失败，而那时原文已经不在了；同时每次正常写入从一次变成两次。`rename` 是这里唯一现成的不可分步骤，备份恢复是在没有它的时候才值得付的代价。

**把临时文件放到 `os.tmpdir()`。** 干净，不会在目标目录里留点痕迹。它输在 `EXDEV`：跨设备 rename 直接失败，于是「原子」在最需要它的那些部署（数据盘和系统盘分开）上恰好不成立。临时文件必须和目标同目录，清理逻辑因此也必须可靠——这就是失败路径上那个 `rmSync` 存在的原因。

**用一个 promise 队列 / async mutex 来串行 `add()`。** 看起来是并发问题的标准答案。它输在两处：`add()` 是被工具同步调用的，store 也必须在插件注册 skill 时同步可读，改成异步会改掉对外的 API 和每一个调用方；更重要的是 JS 事件循环本来就不会交错两个同步 unit，promise 队列防的是一个单线程模型已经防住的东西。真正的危险是 unit 中途挂起，而处理它的正确做法是把那次调用拒绝掉、让调用方重试——这也正是队列实际在做的事。

**继续在两个地方各写一份原子规则。** 一条写在 lesson store 里，一条写在 `prompt_doc_write` 里。短期看改动更小。它输在「一条规则两个家」：下一次只改一边的时候，两边就会在原子性这件事上不一致，而这种不一致没有任何测试会红——两边的测试各自只钉自己那一份。共用一个实现之后，原子性这条规则只有一个家。

**用时间戳或自增计数器代替「按条数推 id」。** 能绕开并发推同一个 id。它输在 `L###` 是文档化的、人读的身份：时间戳会在时钟回拨时乱序，而计数器仍然需要串行化才正确——id 的推导方式不是问题，读-改-写不是一个整体才是问题。

## Consequences

- **需要 Host 重启才生效**，不是刷新页面。`lib/lessons.js` 和 `host.js` 都在 Host 侧，见 [README 五、1](../../../../README.md)。
- `prompt_doc_write` 落盘的字节与普通写路径逐字节相同（有测试钉住），所以「换成原子写入」这件事对产出零影响，只对失败形态有影响。
- 一次失败的写入留下：上一份文档完好、零个临时文件、一条点名目标路径的错误。
- 一次并发 `prompt_doc_learn` 现在得到一条可重试的错误，而不是一条悄悄消失的教训。
- 两条写路径共用一个实现，所以**改原子性规则会同时影响两者**。这是想要的：它保证两边不会各自漂移。
- 并发被拒绝而不是被排队等，意味着调用方（模型）必须会重试。工具的描述和 skill 正文因此要说清「被拒绝就重试」，否则一次拒绝会被读成永久失败。
- `writeMirror` 仍是非原子的，这是已知并刻意的，见上文。

## Testing

[`tests/host-write-safety.test.js`](../../../../tests/host-write-safety.test.js) 钉住三类性质，共 15 个用例：

- `prompt_doc_write`：与普通写路径字节相等、成功后不留临时文件、没有 `overwrite: true` 时仍然拒绝覆盖、`overwrite: true` 时替换、写入失败时不留临时文件、写入失败时上一份文档完好。
- `writeFileAtomic`：一步完成替换并消费临时文件、rename 失败不留临时文件、临时写自身失败不留临时文件、失败时保留原内容。
- `LessonsStore.add`：12 条重叠追加一条不丢且 id 连续唯一、在已有教训之后继续编号、`lessons.json` 格式逐字节不变、后续写入失败时已记的教训仍在、store 文件无法替换时不留临时文件。
